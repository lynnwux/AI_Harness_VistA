# AI Layer (Equipment Inventory Chatbot) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Decide, generate, deploy and verify a chatbot over FileMan file 6914 on IRIS AI Hub: four quick-access questions as SQL templates whose parameters the developer decides in the Decide chat, plus general questions answered by AI-written, guarded SQL, served through a separate Angular chat app.

**Architecture:** A discovery file (`capability-graph/inventory-fields.json`) describes the 6914 tables. The AI layer spec is generated from the graph, the decisions record (new `aiQuestions` section), `implemented.json` and that file, like the other two specs. `agent/ai-runner.js` (started by 🔨 on the AI tab) generates the `EquipmentAI.*` classes (agent, toolset, guard, VADEMO client, chat REST dispatch), deploys them to `iris-ai-hub`/INTEROP with the interclaw scripts, builds and publishes the Angular chat app, and verifies the chatbot's results against direct VADEMO queries.

**Tech Stack:** Node 22 CommonJS, Express 4, `node:test`, no new npm dependencies; ObjectScript with IRIS AI Hub (`%AI.Agent`, `%AI.ToolSet`, `%AI.Provider`, `%AI.Agent.Session`); Angular 20 (scaffolded by `npx @angular/cli@20`, as `build-runner.js` does).

**Spec:** `docs/superpowers/specs/2026-10-20-ai-layer-design.md`

## Global Constraints

- No credential, host or token in source, a spec, the decisions record, or a generated class. Secrets live only in `agent/.env` (git-ignored); placeholders go in `agent/.env.example`. The repo is public.
- Decisions come only from the Decide page's chat tools. Never write `agent/decisions.json` from a dev session; never stage or commit it.
- The developer presses 🔨 themselves. Do not trigger `/api/build*` routes with curl.
- Commit only when the developer asks. Each task's last step says what that commit would contain.
- The chatbot never writes to VistA. The general SQL path accepts a single `SELECT` over allow-listed tables only, enforced in code.
- The chat never proposes a threshold, year or condition the developer has not stated — including the prototype's ($50,000, FY2031).
- All of file 6914 — never the prototype's IEN 401–450 range.
- Show names, not pointer IENs: use the projection's name columns (`EQUIPMENT_CATEGORY_NAME`, `SERVICE_POINTER_NAME`, `LOCATION_ROOM_NUMBER`, `VENDOR_POINTER_NAME`, …).
- AI classes live in package `EquipmentAI`, never `EquipmentEntry`. Namespace `INTEROP`, container `iris-ai-hub`.
- Row cap for any query result returned to the chat: 200 rows, with `truncated: true` when capped.
- Facts checked on 2026-10-20 (read-only): `VISTA.EQUIPMENT_INV_6914` has 112 columns and 295 rows; 11 rows have `MFGR__EQUIPMENT_NAME LIKE '%BED%'`; `WORK_ORDER_6920` and the 6914 sub-file tables exist; `iris-ai-hub` reaches VADEMO on port 80; `%AI.Agent` and `%AI.ToolSet` exist in INTEROP.
- FileMan dates in the SQL projection compare as integers: `CAST(<date col> AS INTEGER)` against `(year-1700)*10000 + month*100 + day` (the prototype's method).
- The federal fiscal year runs October 1 – September 30 (FY2030 = 2029-10-01 … 2030-09-30). This is a fixed fact, not a decision.

## Review Focus

1. A general question that names a pointer field ("by category", "in which room") — answers must show names, not IENs → Task 5 tests that the agent instructions name the `*_NAME` columns and the schema guide marks each pointer column with its name column.
2. A guard bypass through a subquery, a `JOIN`, a comment, lower case, or a second statement (`SELECT … ; DELETE …`, `SELECT … FROM VISTA.EQUIPMENT_INV_6914 WHERE IEN IN (SELECT … FROM %Dictionary…)`) → Task 8's live guard cases include each.
3. A question that returns more than 200 rows ("list all equipment") — the app must say the list is truncated, not imply that's everything → Task 5 (tool JSON carries `truncated`) and Task 7 (the app shows "first 200 of N").
4. VADEMO unreachable or the Bedrock token expired — the chat must say so plainly, never estimate → Task 5 tests the instructions forbid answering without a tool result, and the REST dispatch maps a provider auth failure to the fixed message from the spec.
5. A quick-access question asked for another year in free text ("which capitalized assets age out in FY2032?") — the aging tool takes `fiscalYear` as an argument whose default is the decided year → Task 5 test.

### Task 5: Generate the EquipmentAI classes

**Files:**
- Create: `agent/lib/ai-hub.js`
- Test: `agent/test/ai-hub.test.js`

**Interfaces:**
- Consumes: the AI spec (`detail`), `inventory`.
- Produces: `aiClasses({ ai, inventory, model }) → [{ name, text }]` in compile order:
  - `EquipmentAI.Config` — `ClassMethod Get(key) As %String` reading `^EquipmentAI.Config(key)`; credentials via `Ens.Config.Credentials` ids `EquipmentAIVademo` and `EquipmentAIBedrock` (constants exported as `CREDENTIALS`).
  - `EquipmentAI.Vademo` — `ClassMethod Query(sql) As %DynamicArray`: POST to `Get("vademoPath")` on `Get("vademoServer")`:`Get("vademoPort")` with the stored login; throws on HTTP or SQL error.
  - `EquipmentAI.Guard` — `ClassMethod Check(sql) As %String` → `""` if allowed, else the reason. Rules: strip comments; exactly one statement (no `;` outside string literals); first keyword `SELECT`; reject `INSERT|UPDATE|DELETE|DROP|ALTER|CREATE|GRANT|CALL|EXEC|INTO|TRUNCATE` as words; every identifier after `FROM`/`JOIN` (including subqueries) must be in the generated allow-list; case-insensitive. `ClassMethod Cap(sql) As %String` wraps the query to return at most 201 rows (to detect truncation).
  - `EquipmentAI.Tools` `Extends %AI.ToolSet` — one tool per spec question (method name = id without `AIQ.`, e.g. `AgingOutFY(fiscalYear As %Integer = <decided>)`, others no arguments) running its fixed SQL, plus `RunQuery(sql As %String)` running `Guard.Check` then `Vademo.Query`. Every tool returns JSON `{ tool, sql, columns, rows, rowCount, truncated, error? }` and stores it in `^||EquipmentAI.Last`.
  - `EquipmentAI.Agent` `Extends %AI.Agent` — `PROVIDER = "bedrock"`, `MODEL = <model>`, `TOOLSETS = "EquipmentAI.Tools"`; `INSTRUCTIONS` = rules (answer only from a tool result; every number comes from a query; if a tool errors, say VistA could not be reached and stop; show names via the `*_NAME` columns; say when a result was truncated; read-only) + the schema guide generated from `inventory` (each column: name, DD meaning, codes, and for pointers "use <nameColumn> for the name").
  - `EquipmentAI.Chat` — `ClassMethod Reply(sessionId, message) As %DynamicObject` and `ClassMethod Quick(sessionId, id, fiscalYear) As %DynamicObject`, following the prototype's session pattern (`%AI.Agent.Session`, export/import in `^EquipmentAI.Sessions`). `Quick` calls the tool method directly, then asks the agent to word that result. Both return `{ reply, tool, sql, columns, rows, rowCount, truncated, error? }` from `^||EquipmentAI.Last`. A provider authentication failure returns `error: "Bedrock token expired — update it in agent/.env and press 🔨 again"`.
  - `EquipmentAI.REST.Dispatch` `Extends %CSP.REST` — `POST /chat`, `POST /quick/:id`, `POST /guard` (`{ sql }` → `{ ok, reason }`, used by the build's verification). Web app `/equipmentai` (exported `WEB_APP`).
- Produces: `PKG = "EquipmentAI"`, `WEB_APP`, `CREDENTIALS`.
